Configuración única de la USB en usbipd

Conectar la USB, identificar su BUSID y compartirla con WSL. Solo se hace una vez por memoria.

PowerShell como administrador:

usbipd list                      # find "USB Mass Storage Device", e.g. BUSID 1-2
usbipd bind --busid 1-2

Lista de comprobación antes de la demostración

  • El repositorio compila: .\scripts\build-image.ps1 termina sin errores.
  • La clave de recuperación de BitLocker está anotada (cuenta Microsoft → Dispositivos → Claves de recuperación).
  • Se conoce la tecla de configuración del firmware (Lenovo V14 G4: F2) y la del menú de arranque (F12, o Fn + F12).
  • La USB no contiene datos que se necesiten.
  • Hay una cámara o celular para fotografiar el arranque físico.

Demostración paso a paso

Paso 1 — Compilar el programa de arranque y generar la imagen

Requisitos 1, 3 y 4 · Programa propio, construcción del medio, preparador propio
.\scripts\build-image.ps1

Salida esperada:

[1/3] Building boot program...
OK: C:\Users\sebas\Desktop\repos\bareboot\build\esp\EFI\BOOT\BOOTX64.EFI
[2/3] Building preparer (Linux and Windows)...
[3/3] Building disk image...
image written: /mnt/c/Users/sebas/Desktop/repos/bareboot/build/bareboot.img (3072-byte boot program)

Qué explicar: main.c se compila con clang + lld-link como aplicación UEFI (BOOTX64.EFI, 3072 bytes). Luego la herramienta Go escribe, con código propio, una imagen de disco con tabla GPT, partición ESP en FAT32 y el programa en \EFI\BOOT\BOOTX64.EFI.

Paso 2 — Verificar la imagen con herramientas independientes

Requisito 3 · Regla “Formato coherente”
.\scripts\verify-image.ps1
[PASS] GPT - sgdisk -v
[PASS] ESP type - partition 1 has the EFI System Partition GUID
[PASS] FAT32 - fsck.vfat -n (read-only check)
[PASS] Files - \EFI\BOOT\BOOTX64.EFI present
[PASS] Contents - SHA-256 ...

Image verified.

Qué explicar: estas comprobaciones las hacen herramientas de Linux que no forman parte del proyecto (sgdisk, fsck.vfat, mtools). Si el código escribiera mal un CRC o un campo del FAT32, fallarían.

La herramienta también tiene su propia verificación:

wsl --cd C:\Users\sebas\Desktop\repos\bareboot\build -e ./preparer-linux verify -image bareboot.img

Paso 3 — Arrancar la imagen en una máquina virtual

Requisito 9 · Prueba virtual
.\scripts\run-qemu.ps1

Se abre una ventana de QEMU. Tras el logo de TianoCore aparece el banner de bareboot con Firmware: EDK II. Hacer clic dentro de la ventana y pulsar una tecla: el programa devuelve el control y el firmware abre su menú de configuración. Cerrar la ventana para terminar.

Qué explicar: QEMU emula un PC con firmware UEFI (EDK II). El firmware lee la GPT de la imagen, encuentra la ESP, carga BOOTX64.EFI y llama a efi_main. El menú gris del final es la prueba de que el programa retornó correctamente al firmware.

Paso 4 — Conectar la USB y detectar los discos

Requisito 5 · Identificación del destino · Regla “Destino seguro”

4.1 Mantener WSL encendido: abrir una terminal aparte y dejarla abierta con:

wsl -e sleep 7200

4.2 Pasar la USB a WSL (en otra terminal):

usbipd attach --wsl --busid 1-2
usbipd list                      # state must be "Attached"

4.3 Listar los discos:

.\scripts\preparer.ps1 list
DISK  BUS   SIZE       MODEL                 VOLUMES  STATUS
sda   SCSI  722.9 MiB  Msft Virtual Disk     -        REJECTED: not a USB disk (bus: SCSI)
sdd   SCSI  1.0 TiB    Msft Virtual Disk     /        REJECTED: system disk (holds the running OS);
                                                       not a USB disk (bus: SCSI)
sde   USB   922.0 MiB  Generic Mass-Storage  -        OK - can be used

5 disk(s) found, 1 eligible.

Qué explicar: la herramienta lee la información de cada disco (en Linux desde /sys/block; en Windows con DeviceIoControl) y aplica reglas de seguridad: rechaza el disco del sistema, los que no son USB, los que no reportan identidad, los demasiado pequeños y los de sector distinto de 512 bytes.

El nombre puede cambiar sde depende del orden de detección. Usar siempre el nombre que muestre list en ese momento en los pasos siguientes.

Paso 6 — Preparar la USB

Requisitos 4, 6 y 7 · Preparador propio, confirmación, progreso y resultado · Regla “Escritura completa”
.\scripts\preparer.ps1 write -disk sde

La herramienta muestra el resumen del destino y lo que se escribirá, advierte que se perderá todo el contenido y pide la frase de confirmación. Escribir exactamente ERASE DISK sde:

Target disk
  Disk:        sde (/dev/sde)
  Model:       Generic Mass-Storage
  Bus:         USB
  Capacity:    922.0 MiB (966787072 bytes, 512-byte sectors)
WARNING: ALL DATA ON THIS DISK WILL BE LOST. ...

Type "ERASE DISK sde" to continue, or anything else to cancel: ERASE DISK sde
Releasing the volumes of disk sde (lock/unmount)...
[1/3] Writing boot media...
  [##############################] 100%  1.0 MiB / 1.0 MiB
[2/3] Flushing pending writes to the device...
[3/3] Verifying...
  [OK  ] read-back: 1.0 MiB in 15 regions identical to what was written
  [OK  ] GPT: protective MBR, primary and backup headers and entries valid (CRC32)
  [OK  ] ESP: "EFI System Partition", LBA 2048-133119 (64.0 MiB)
  [OK  ] FAT32: boot sector and both FATs valid, \EFI\BOOT\BOOTX64.EFI found
  [OK  ] boot program: 3072 bytes, identical to the source file

Done: disk sde prepared and verified (1.0 MiB written).

Qué explicar: antes de escribir se vuelve a consultar el disco para comprobar que sigue siendo el mismo dispositivo. Se desmontan sus volúmenes, se escribe con barra de progreso, se sincroniza (fsync), se descarta la caché y se verifica dos veces: relectura byte a byte de las 15 escrituras y lectura de la GPT, la ESP y el FAT32 como lo haría el firmware.

Opcional, verificación con herramientas externas directamente sobre la USB:

wsl -u root -e sh -c 'PATH=/usr/sbin:$PATH; sgdisk -v /dev/sde; fsck.vfat -n /dev/sde1'

Paso 8 — Arranque físico desde la USB

Requisitos 2 y 10 · Tipo de arranque, arranque físico · Regla “Compatibilidad comprobada”

8.1 Suspender BitLocker (solo si el disco está cifrado). PowerShell como administrador:

manage-bde -status C:                                  # "Protection On" means encrypted
manage-bde -protectors -get C: -Type RecoveryPassword  # ID must match the saved key
manage-bde -protectors -disable C: -RebootCount 0
manage-bde -status C:                                  # must say "Protection Off"

8.2 Entrar al firmware y desactivar Secure Boot. PowerShell como administrador:

shutdown /r /fw /t 0

En el firmware: pestaña Security → Secure Boot → Disabled. Guardar y salir con F10.

8.3 Arrancar desde la USB. Con la USB conectada, al encender pulsar repetidamente F12 (o Fn + F12) y elegir la opción USB Generic Mass-Storage.

Resultado esperado: el banner de bareboot con Autor: Sebastian Cohen y Firmware: Phoenix Technologies Ltd. Al pulsar una tecla, el firmware continúa con la siguiente opción de arranque (Windows) o vuelve a su menú.

Qué explicar: la línea Firmware la responde el firmware del equipo a través de SystemTable->FirmwareVendor; en QEMU decía EDK II y aquí dice Phoenix, lo que prueba que el código corre sobre el hardware real. Secure Boot se desactiva porque BOOTX64.EFI no está firmado con una clave reconocida por el firmware.

Paso 9 — Restaurar la seguridad del equipo

Regla “Compatibilidad comprobada”: no dejar cambiadas las opciones de seguridad

9.1 Entrar otra vez al firmware (PowerShell como administrador: shutdown /r /fw /t 0) y poner Secure Boot → Enabled. Guardar con F10.

9.2 Ya en Windows, PowerShell como administrador:

manage-bde -protectors -enable C:
Confirm-SecureBootUEFI        # must return True
manage-bde -status C:          # must say "Protection On"
Orden obligatorio Primero se activa Secure Boot y después se reactiva BitLocker. Al revés, el TPM registraría el estado sin Secure Boot y pediría la clave de recuperación en el siguiente arranque.

9.3 Devolver la USB a Windows (opcional): usbipd detach --busid 1-2.

Demostraciones adicionales

Detección de corrupción

Muestra que la verificación detecta un solo byte alterado. Se trabaja sobre una copia; la imagen original no se toca.

# Copy the image and change one byte inside BOOTX64.EFI
$b = "C:\Users\sebas\Desktop\repos\bareboot\build"
Copy-Item "$b\bareboot.img" "$b\bad.img"
$fs = [IO.File]::Open("$b\bad.img", 'Open', 'ReadWrite')
$fs.Position = 1048576 + (2080 + 3) * 512 + 10; $fs.WriteByte(0xAA); $fs.Close()
wsl --cd $b -e ./preparer-linux verify -image bad.img
Remove-Item "$b\bad.img"
  [OK  ] GPT: ...
  [OK  ] FAT32: ...
  [FAIL] BOOTX64.EFI on the media (3072 bytes) differs from the boot program (3072 bytes)
error: NOT a valid bareboot media: ...

Otros desplazamientos para probar: 552 (encabezado GPT principal, falla el CRC32), 1048589 (sectores por cluster del FAT32).

Compilación reproducible

.\boot\build.ps1; (Get-FileHash .\build\esp\EFI\BOOT\BOOTX64.EFI).Hash
.\boot\build.ps1; (Get-FileHash .\build\esp\EFI\BOOT\BOOTX64.EFI).Hash   # same hash

Estructura del disco con herramientas de Linux

wsl -u root -e lsblk -o NAME,SIZE,FSTYPE,LABEL,PARTLABEL,PARTTYPENAME /dev/sde
wsl -u root -e sh -c 'PATH=/usr/sbin:$PATH; sgdisk -p /dev/sde'

Versión de Windows de la herramienta

En un equipo sin Smart App Control, la herramienta funciona directamente en Windows con la API Win32. PowerShell como administrador, desde build\:

.\preparer.exe list                 # the USB appears as disk 1, the system disk as 0
.\preparer.exe write -disk 1
.\preparer.exe verify -disk 1

En el equipo de desarrollo este ejecutable lo bloquea Smart App Control (“An Application Control policy has blocked this file”), motivo por el que la escritura se hace desde WSL.

Solución de problemas

SíntomaCausa probable y solución
usbipd: error: There is no WSL 2 distribution runningWSL está apagado. Dejar abierta una terminal con wsl -e sleep 7200 y repetir usbipd attach.
La USB no aparece en preparer listNo está conectada a WSL: usbipd list debe mostrar Attached. El BUSID puede cambiar si se conecta en otro puerto.
La USB aparece con otro nombre (sdf…)Normal: usar el nombre que muestre list.
verify falla solo en boot program ... differsLa USB tiene una versión anterior del programa. Volver a grabarla con write.
build-image.ps1 falla en el paso 3WSL no responde o falta build\preparer-linux. Comprobar wsl -e echo ok.
PowerShell no permite ejecutar los scriptsSet-ExecutionPolicy -Scope CurrentUser RemoteSigned
manage-bde: “access was denied”La terminal no es de administrador.
La USB no aparece en el menú F12Habilitar el arranque por USB en el firmware; probar otro puerto.
Se elige la USB pero vuelve al menú sin mostrar nadaSecure Boot sigue activo.
Windows pide la clave de recuperación de BitLockerSe cambió Secure Boot sin suspender la protección. Introducir la clave de 48 dígitos; Windows arranca normalmente.
El firmware no muestra el banner y entra a WindowsLa USB no se eligió en el menú de arranque o no contiene un medio válido (comprobar con verify).
